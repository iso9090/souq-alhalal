# تجهيز سجل Super Admin — لم تنفذ Migration

تحديث 9 سبتمبر 2026: هذا وصف تاريخي لمرحلة تجهيز السجل. فحص المرحلة الثانية للقراءة فقط وجد السجل موجودًا والتفويض مفعّلًا ومالكًا واحدًا نشطًا، باستخدام ADC سابق. لم يُغير الفحص السجل أو claims. راجع [حالة الخدمات وخطة ربط البريد الأحدث](../LIVE_SERVICES_SETUP.md).

السلطة القديمة هي custom claim `admin: true`، ومواضع التحقق: `app.js/requireAdminClaim` يقرأ `getIdTokenResult`، ثم `admin-permissions.js/accessModel` يحدد الدور. تفرض `firestore.rules/isAdmin` نفس الشرط على الخادم.

قبل وجود `adminSecurity/config` يبقى المدير القديم يعمل. بعد وجود السجل لا يكفي claim وحده؛ يلزم أيضًا إدراج الحساب في `superAdminUids`. `enabled` يتحكم في تفويض المساعدين فقط، وليس في إلزامية سجل المالكين. غياب السجل أو قائمة مالكين فارغة لا يفعّل المساعدين.

السجل مستند مستقل في collection `adminSecurity` وليس ضمن users. الحقول المطلوبة: `superAdminUids` قائمة كاملة غير فارغة، و`enabled` قيمة Boolean. يضيف سكربت التهيئة `schemaVersion: 1` و`initializedAt` و`bootstrapDigest` للمراجعة. ينشئ أيضًا مستند حماية `adminAccess/{owner}` بدور super_admin، دون تعديل ملفات users أو claims.

جميع كتابات العميل إلى adminSecurity ممنوعة، بما فيها المالك والمساعد والمستخدم العادي. حذف مستندات adminAccess ممنوع أيضًا. لذلك لا يمكن لأي عميل حذف آخر مالك أو إضافة نفسه. السكربت يرفض صفر مالكين، غياب مالك نشط، تغيير قائمة المالكين الموجودة، أو الكتابة فوق سجل دور متعارض. لا يحتوي عملية إزالة مالك. صلاحيات IAM/Admin SDK تتجاوز Rules؛ حماية هذه البيئة مسؤولية التشغيل الموثوق ولا تستطيع Rules تقييدها.

## السكربت

`prepare-super-admin-registry.mjs` يستخدم Firebase Admin SDK الرسمي وApplication Default Credentials المصرح بها سابقًا. لا يستخرج tokens من Firebase CLI ولا يولّد مفاتيح أو كلمات مرور. ثبّت SDK في بيئة أدوات موثوقة مع حل module resolution المعتاد، خارج حزمة الموقع. لا تضع credentials في Git.

أمر القراءة فقط، للمراجعة المستقبلية في البيئة الموثوقة:

```text
node admin-tools/prepare-super-admin-registry.mjs --project souq-al-halal-9e3e8 --dry-run
```

إغفال `--dry-run` يبقي الوضع قراءة فقط. إغفال المشروع أو تمرير مشروع Production آخر مرفوض. لا تقبل مشاريع demo إلا مع محاكي Auth وFirestore على loopback. لا تستخدم هذا الأمر كدليل على تنفيذ فحص Production في هذه المهمة.

السكربت يجلب جميع صفحات Auth ويختار claims الفعلية، ويفحص حالات ملفات أصحاب claims. المخرجات أعداد وdigest فقط؛ لا تطبع المعرفات الكاملة أو بيانات الحسابات. لا يحفظ ملف credentials أو قائمة مستخدمين.

الكتابة المستقبلية تحتاج `--apply` بالإضافة إلى كتابة عبارة تأكيد تشمل اسم المشروع وبصمة مجموعة المالكين في طرفية تفاعلية. الإدخال عبر pipe مرفوض. بعد التأكيد يعيد فحص claims ثم ينشئ السجل وسجلات الحماية في معاملة واحدة، مع `enabled: false` دائمًا. لا ينشر Rules ولا يمكّن المساعدين. إعادة التشغيل على سجل مطابق لا تكتب شيئًا. اختلاف مجموعة المالكين يوقف العملية بدل توسيعها تلقائيًا.

Auth وFirestore لا يدعمان معاملة مشتركة. قبل التهيئة الفعلية أوقف إداريًا أي تغييرات متزامنة على claims، راجع جميع المالكين، واحفظ نسخة من القواعد والسجل. أي حساب مالك معطل أو غير نشط يمنع مرحلة الكتابة ويحتاج مراجعة منفصلة؛ السكربت لا يصلحه. تفعيل المساعدين لاحقًا إجراء مستقل بعد مراجعة ونشر القواعد والواجهة بموافقة منفصلة.

## حالة هذه المهمة

- لم يتم تشغيل Migration أو إجراء أي كتابة Production.
- لم يوجد firebase-admin محليًا ولا إعداد ADC صريح أو ملف ADC الافتراضي في البيئة المفحوصة؛ لم نحاول تجاوز ذلك عبر credentials أخرى.
- لذلك عدد حسابات Production الحاملة `admin: true` **غير متحقق منه**، ولا يمكن تأكيد إن كانت أكثر من واحد. يحدده dry-run الرسمي في البيئة الموثوقة لاحقًا، قبل اعتماد قائمة المالكين.
- اختبارات السكربت تستخدم خدمات مصطنعة؛ اختبارات الصلاحيات تستخدم Firestore Emulator. لا يُدّعى أنها تجربة Admin SDK فعلية على Production.
- القواعد الجديدة لم تنشر. حساب المدير الحالي في Production لم يتغير، ولا يوجد lockout ناتج عن هذه المهمة.
